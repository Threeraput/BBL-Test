Product context

Two services for a personal bookmark manager — a private read-later app. A signed-in person saves links, organises them into collections, and nobody else can see any of it.

Core invariant: Everything in this app is private to the person who created it. There is no public content, no shared feed, no "browse other users." If user A can see, edit, or even learn of the existence of user B's data, the app is broken.

Requirements & decisions to justify (log the justification in DECISIONS.md):

Must use Authorization Code flow with PKCE (S256). No implicit flow.
Decide which token the API accepts as the Bearer credential. State the choice and rationale — this must be defensible in depth later.
Don't assume — verify. Inspect the tenant's discovery document and JWKS to determine which flows, tokens, and signing algorithms are actually available before committing to a design.
Two resources, /collections and /bookmarks, each supporting: get one, list, create, update (PUT), patch (PATCH), delete, and filtering. Plus a /me endpoint returning the current signed-in person. Suggested shape — refine as needed, and justify any changes in DECISIONS.md:
Resource	Fields
Collection	id, name, ownerId, createdAt, updatedAt
Bookmark	id, url, title, notes?, collectionId?, ownerId, createdAt, updatedAt
A bookmark belongs to a collection (nullable — a bookmark can be uncategorised), and both belong to a person. Support GET /collections/:id/bookmarks.
SQL persistence for every route.
Prisma as the ORM.
Seed data for at least two distinct users.
Frontend website
React with Vite, TypeScript. No Next.js.
React Router ≥ v8 for navigation.
MUI ≥ v9 for UI components.
Integrates with the backend API above.
Two pages:
/collections — list collections, view one, create, delete.
/bookmarks — list bookmarks, view details, create, delete, filter by collection.
Under-specified requirement (resolve and document in DECISIONS.md)

Collections hold bookmarks. A user can delete a collection. A user may want to share a collection with someone else.

Does not have to be fully implemented — decide the scope, justify it, and back up whatever ships with tests.

Optional bonuses (only after the above is solid)
Dockerfile — containerise the backend, the frontend, or both.
CI/CD — a pipeline that builds and checks the project on every push.
An /all page — a third frontend page showing collections together with the bookmarks inside them, rather than the two lists side by side.
Full-text search — search across bookmark titles and notes.

Note: modelling the collections ↔ bookmarks relation and exposing it over the API is core work, not a bonus. Only the /all page is a bonus here.

End-to-end goal

Log in via Authorization Code + PKCE, obtain token(s), and drive the UI against the authenticated API with data persisted in SQL via Prisma.
